# 为什么 QUIC 能比 TCP 更快

要理解 QUIC，先要理解它替换掉了什么。传统 HTTPS 建立在 TCP 之上，而 TCP 的连接建立需要三次握手：客户端发送 SYN，服务端回应 SYN-ACK，客户端再回 ACK。这意味着一来一回，至少消耗一个完整的往返时间（RTT）。如果再加上 TLS 握手，一次完整的 HTTPS 首次连接通常需要 2 到 3 个 RTT 才能开始传输应用数据。

QUIC 把传输层和加密层合并了。它在第一个数据包里就同时携带连接建立和密钥协商所需的信息，因此首次连接只需要 1 个 RTT；而对于访问过的站点，客户端缓存了服务端的配置信息，可以实现 0-RTT，也就是在第一个包里就带上应用数据。这就是为什么在高延迟网络下，QUIC 的首屏时间改善最明显——延迟越高，省下的 RTT 绝对值越大。

另一个差异在于队头阻塞的范围。TCP 是严格按序交付的字节流，如果第 3 个数据包丢失，即使第 4 到第 10 个包已经到达，接收端也无法把它们交给应用层，必须等第 3 个包重传。这个问题在 HTTP/2 上尤其致命，因为 HTTP/2 把多个请求复用到同一条 TCP 连接上，一个丢包会卡住所有请求，被称为 TCP 层的队头阻塞。

QUIC 在传输层实现了独立的流（stream）。每条流有自己的序号空间和重传逻辑，一条流上的丢包不影响其他流的数据交付。所以在弱网环境下，QUIC 的多请求并发表现明显好于 HTTP/2 over TCP。需要注意的是，QUIC 并没有消除队头阻塞，它消除的是跨流的队头阻塞；单条流内部丢包仍然要按序等待。

第三个差异是连接迁移。TCP 连接由四元组标识：源 IP、源端口、目的 IP、目的端口。手机从 Wi-Fi 切换到蜂窝网络时，源 IP 变了，四元组不再匹配，连接必须重建，正在进行的下载或视频通话会中断。QUIC 用一个 64 位的连接 ID 标识连接，与 IP 地址解耦。只要连接 ID 不变，即使网络路径变了，连接仍然可以继续，这就是所谓的连接迁移。

不过 QUIC 也有代价。它运行在 UDP 之上，而部分企业网络和运营商会对 UDP 进行限速甚至封锁，导致 QUIC 连接失败或性能劣化。因此生产环境中的浏览器通常会实现竞速机制：同时尝试 QUIC 和 TCP，谁先完成握手就用谁，并在 QUIC 连续失败后暂时退回 TCP。另外 QUIC 的所有数据都在用户态处理，加解密开销比内核态的 TCP 更高，在低端设备上 CPU 占用会成为新的瓶颈。

最后一点常被误解：QUIC 快，主要快在连接建立和弱网恢复，而不是稳态吞吐。在低延迟、无丢包的理想网络里，QUIC 与优化良好的 TCP 差距很小，有时因为用户态开销反而略慢。
